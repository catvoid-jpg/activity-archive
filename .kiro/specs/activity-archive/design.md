# Design Document

## Overview

활동기록 아카이브는 초대 코드로 진입한 소수 사용자가 활동 경험을 START(Situation, Task, Action, Result, Taken) 구조로 축적하고, 지원서 문항에 맞는 경험 소재를 스스로 찾도록 돕는 웹서비스이다. 이 설계는 확정된 요구사항(requirements.md), 제약사항(constraints-closed.md), 태그 정의(tags.md)를 구현으로 옮기기 위한 것이며, 원문에 없는 기능·임계값·타이밍·재시도 정책을 추가하지 않는다.

핵심 설계 원칙은 **AI는 질문하고 분류하되 사용자의 경험을 대신 서술하지 않는다**는 것이다. 이 원칙은 AI 호출 지점을 3개(심화 질문 생성, 태그 부여, 지원서 문항 분석)로 한정하고, 내보내기·복사·저장 경로에서 AI를 배제하는 구조로 반영된다.

설계 상 지켜지는 경계는 다음과 같다.

- **프론트엔드/백엔드 분리.** 활동 기록·빠른 기록·일기 메타(날짜·태그)는 서버 DB에, 일기 본문은 브라우저 로컬 저장소에만 저장한다.
- **AI 호출은 서버에서만.** 클라이언트는 외부 LLM API를 직접 호출하지 않는다. API 키를 포함한 비밀값은 서버 환경변수로만 다루고 소스코드에 하드코딩하지 않는다.
- **초대 코드가 사용자 식별자.** 모든 조회·삭제 요청은 서버에서 초대 코드 소유권을 검증한다.
- **무료 티어 운영.** 상시 백그라운드 작업, 별도 캐시 서버·큐·검색 엔진을 도입하지 않는다. HTTPS로 서비스한다.
- **모바일 우선 단일 컬럼.** 미디어 쿼리 기준점 1개, 다단 레이아웃·애니메이션·컴포넌트 라이브러리 없음. CSS 300줄 이하.

_관련 요구사항: Requirement 1, 12, 13, 14, 15, 16, 17._

## Architecture

### 구성 요소

```
[Client (모바일 우선 SPA)]
  ├─ 초대 코드 진입 화면
  ├─ 활동 기록 화면 (등록/조회/삭제, 답변 수정)
  ├─ 빠른 기록 화면
  ├─ 심화 질문/답변 화면
  ├─ 일기 화면 (본문 = 로컬 저장소, 메타 = 서버)
  ├─ 소재 추천 화면
  └─ 온보딩/안내 화면
        │  HTTPS (JSON)
        ▼
[Backend API Server]
  ├─ 초대 코드 검증 · 소유권 미들웨어
  ├─ 활동 모듈        (활동/답변 CRUD, 메타 수정 불가)
  ├─ 빠른 기록 모듈
  ├─ 일기 메타 모듈    (날짜 + 태그만)
  ├─ 소재 추천 모듈
  ├─ AI 연동 모듈  ★ 유일한 LLM 호출 지점
  │     ├─ 사전 차단: 전역 월간 상한 검사 → 입력 길이 검사
  │     ├─ 호출: 심화 질문 생성 / 태그 부여 / 문항 분석
  │     └─ 사후 검증: 응답 파싱 · 태그 목록 검증(목록 밖 폐기)
  └─ 태그 상수 (tags.md 고정 목록: 상위 10 / 하위 35 / START 표기)
        │
        ▼
[관계형 DB (무료 티어)]
```

### 핵심 흐름

- **AI 호출 게이트.** 심화 질문 생성·태그 부여·문항 분석 요청은 모두 AI 연동 모듈을 통과한다. 모듈은 호출 **이전에** (1) 전역 월간 호출 상한, (2) 단일 요청 입력 길이 상한을 검사하고, 어느 하나라도 초과하면 LLM을 호출하지 않고 안내 응답을 반환한다. 호출 **이후에는** 응답을 파싱하고 태그 상수 목록에 대조하여 목록 밖 값을 폐기한 뒤에만 결과를 사용한다. 파싱 실패 시 재시도 없이 실패로 처리한다.
- **비 AI 경로.** 빠른 기록 저장, 일기 저장, 답변 수정, 내보내기, 복사는 AI 연동 모듈을 거치지 않는다.
- **일기 경계.** 일기 본문은 클라이언트 로컬 저장소에만 저장되고 서버로 전송되지 않는다. 서버에는 일기의 날짜와 선택된 태그만 저장된다.
- **소유권 검증.** 초대 코드는 요청 헤더로 전달되고, 조회·삭제 API는 대상 레코드의 소유 초대 코드와 대조하여 불일치 시 거부한다.

### 상한 처리 방식

전역 월간 AI 호출 상한과 단일 요청 입력 길이 상한은 **서버 설정값(환경변수/설정 상수)** 으로 둔다. 구체 수치는 요구사항·제약 문서에 명시되어 있지 않으므로 임의로 고정하지 않고 설정값으로 노출하며, 사용자별 사용량 집계·표시는 하지 않고 전역 카운트만 유지한다.

_관련 요구사항: Requirement 4, 5, 8, 11, 12, 13, 14, 15._

## Components and Interfaces

모듈은 제약사항의 구현 모듈 구분(초대 코드 진입, 활동 기록, 빠른 기록, AI 연동, 일기, 소재 추천)에 맞춘다. 아래 API는 모두 HTTPS·JSON이며, 초대 코드 진입 API를 제외한 모든 요청은 소유권 미들웨어를 통과한다.

### 초대 코드 진입 모듈

- `POST /api/session` — 초대 코드 검증. 유효하면 식별자로 인정하고 최초 진입 여부(온보딩·시드 필요 여부)를 반환. 유효하지 않으면 거부 + 안내 메시지.
- 클라이언트는 진입 상태를 브라우저에 유지하여 재입력을 요구하지 않는다.

_Requirement 1, 9._

### 활동 기록 모듈

- `POST /api/activities` — 활동 등록(활동명, 기간, 소속, 유형, Situation, Task).
- `GET /api/activities` — 소유 활동 목록 조회.
- `GET /api/activities/{id}` — 활동 상세(START 5요소 + 부여된 태그).
- `DELETE /api/activities/{id}` — 활동 삭제(시드 활동 포함).
- `PATCH /api/activities/{id}/answers/{answerId}` — 심화 질문 **답변 텍스트만** 수정. AI 재호출 없음, 기존 태그 유지. 활동 메타정보(활동명·기간·소속·유형)는 수정 엔드포인트를 제공하지 않는다.

_Requirement 2, 7._

### 빠른 기록 모듈

- `POST /api/quick-notes` — 한 줄 기록 저장(AI 미호출).
- `GET /api/quick-notes` — 날짜순 목록 조회.
- `POST /api/quick-notes/{id}/convert` — 활동으로 전환. 전환 후 심화 질문 생성 흐름으로 이어진다.

_Requirement 3._

### AI 연동 모듈 (유일한 LLM 호출 지점)

내부 공통 파이프라인: `상한 검사 → 입력 길이 검사 → LLM 호출 → 파싱 → 검증`. 세 지점만 이 모듈을 사용한다.

- `POST /api/activities/{id}/questions` — 심화 질문 생성. Situation·Task 기반, Action·Result·Taken 관점, 활동당 최대 4개. 생성 실패 시 사전 정의 기본 질문 목록 반환.
- `POST /api/activities/{id}/tags` — 태그 부여. 답변 텍스트 + 태그 상수 목록 + START 표기를 프롬프트에 포함. Action 답변은 [A], Result 답변은 [R], Taken 답변은 [T] 태그를 우선 판별. 하위 태그는 답변 하나당 최대 2개, 활동 전체 최대 6개. 목록 밖 값 폐기. 실패해도 답변 저장은 정상 완료되며 사용자가 수동으로 태그를 추가할 수 있다.
- `POST /api/recommendations` — 지원서 문항 분석. 문항이 요구하는 상위·하위 태그를 판별(소재 추천 모듈이 소비).

_Requirement 4, 5, 8, 12, 15._

### 소재 추천 모듈

- AI 연동 모듈의 문항 분석 결과를 받아, 하위 태그 일치 활동을 우선 제시하고, 없으면 상위 태그 기준으로 재탐색한다.
- 태그가 일치하는 일기의 **날짜만** 함께 제시한다(본문 미제시). 일기 태그는 클라이언트가 로컬 본문과 무관하게 서버의 일기 메타에서 조회한다.
- 관련 기록이 없으면 안내 메시지를 표시한다.
- 제시된 활동의 START 5요소·태그를 **원본 텍스트 그대로** 클립보드로 복사한다(가공·요약·문장 생성 없음).
- 결과 화면에 지원서 문장을 생성하지 않는 이유를 한 문장으로 표시한다.

_Requirement 8, 10._

### 일기 모듈 (클라이언트 중심)

- 본문 저장/조회/파일 내려받기는 클라이언트 로컬 저장소에서 처리한다.
- `POST /api/diary-meta` — 일기의 날짜 + 선택된 태그만 서버에 저장.
- `GET /api/diary-meta` — 날짜순 메타 목록 조회(본문 없음).
- 태그 선택 화면은 태그 상수 목록을 쓰되 START 표기는 표시하지 않는다.
- 로컬 저장소를 사용할 수 없으면 일기 기능을 비활성화하고 사유를 안내한다.
- 저장된 일기가 하나 이상일 때만 내려받기 버튼을 표시한다.

_Requirement 6, 7, 11._

### 온보딩·안내·서비스 메시지 (클라이언트)

- 최초 진입 시 시드 활동 2개(고정 데이터, AI 미호출)를 예시 표시와 함께 제공하고, 설계 원칙 안내 화면을 표시한다. 안내 화면은 닫으면 재표시하지 않는다.
- 안내 문구는 하드코딩 고정 텍스트로 각 위치당 2문장 이하. 첫 진입 안내·소재 추천 결과·일기 화면·심화 질문 화면에 지정된 고지 문구를 표시한다.

_Requirement 9, 10, 17._

### 프론트엔드 레이아웃

- 모바일 우선, 세로 단일 컬럼. 미디어 쿼리 기준점 1개로 넓은 화면에서 최대 너비 제한 + 가운데 정렬 + 여백 조정만 적용. 별도 모바일 전용 컴포넌트·다단 레이아웃·애니메이션 없음. 컴포넌트 라이브러리 미사용, CSS 300줄 이하, 어떤 너비에서도 가로 스크롤 없음.

_Requirement 16._

## Data Models

일기 본문은 서버에 저장하지 않으므로 데이터 모델에 포함하지 않는다. 태그 목록은 DB 테이블이 아니라 **서버 측 상수**(tags.md 확정 목록)로 구현한다. 서버 DB 테이블은 아래 5개로 한정한다(제약: 5개 이하).

### 1. `invite_code`
| 컬럼 | 설명 |
|------|------|
| code (PK) | 사전 발급된 초대 코드. 사용자 식별자 역할 |
| onboarded_at | 온보딩·시드 제공 완료 시각(최초 진입 판별용, nullable) |
| created_at | 발급 시각 |

### 2. `activity`
| 컬럼 | 설명 |
|------|------|
| id (PK) | 활동 식별자 |
| invite_code (FK) | 소유 초대 코드 |
| name | 활동명 (등록 후 수정 불가) |
| period | 활동 기간 (등록 후 수정 불가) |
| affiliation | 소속 기관 (등록 후 수정 불가) |
| type | 활동 유형: 인턴십/대외활동/프로젝트/학업/기타 (등록 후 수정 불가) |
| situation | Situation 텍스트 |
| task | Task 텍스트 |
| is_seed | 시드 활동 여부(예시 표시용) |
| created_at | 등록 시각(경과일 계산 기준) |

### 3. `activity_answer`
| 컬럼 | 설명 |
|------|------|
| id (PK) | 답변 식별자 |
| activity_id (FK) | 소속 활동 |
| start_element | 답변이 대응하는 START 요소: A / R / T |
| question_text | 심화 질문 텍스트(생성 또는 기본 질문) |
| answer_text | 사용자 답변(수정 가능, 수정 시 AI 재호출 없음) |
| assigned_tags | 부여·수동 편집된 하위 태그 목록(태그 상수 값만 허용, 답변 하나당 최대 2개·활동 전체 최대 6개). 각 태그의 상위 태그는 상수에서 결정 |
| created_at | 생성 시각(경과일 계산 기준) |

### 4. `diary_meta`
| 컬럼 | 설명 |
|------|------|
| id (PK) | 메타 식별자 |
| invite_code (FK) | 소유 초대 코드 |
| entry_date | 일기 날짜 (본문 없음) |
| selected_tags | 사용자가 직접 선택한 태그 목록(태그 상수 값만) |
| created_at | 생성 시각 |

### 5. `quick_note`
| 컬럼 | 설명 |
|------|------|
| id (PK) | 빠른 기록 식별자 |
| invite_code (FK) | 소유 초대 코드 |
| text | 한 줄 기록 텍스트 |
| created_at | 생성 시각 |

빠른 기록은 전용 `quick_note` 테이블(id, invite_code, text, created_at)에 저장하는 것으로 확정한다. 이에 따라 **총 테이블 수는 5개**이며, 이는 여전히 **5개 이하** 제약을 충족한다.

_관련 요구사항: Requirement 2, 3, 5, 6, 7, 12; 경과일은 저장된 레코드의 `created_at`/`entry_date`로 계산하고 별도 집계 테이블을 두지 않는다._

## Error Handling

| 상황 | 처리 | 근거 |
|------|------|------|
| AI 호출 실패 | 안내 메시지 표시 + 이전 화면 상태 유지, 재시도 없음 | Requirement 11.1, 제약(파싱 불가 시 재시도 안 함) |
| 네트워크 오류 | 작성 중이던 답변을 클라이언트에 보존하여 소실 방지 | Requirement 11.2 |
| 전역 월간 AI 상한 도달 | AI 호출 이전 단계에서 차단 + 차단 사유 안내 | Requirement 11.3, 15.1 |
| 단일 요청 입력 길이 상한 초과 | LLM 호출하지 않고 안내 | 제약(AI 호출) |
| AI 응답 파싱 불가 | 재시도 없이 실패 처리 | 제약(AI 호출) |
| AI가 목록 밖 태그 반환 | 해당 값 폐기, 검증 통과 값만 사용 | Requirement 12.4 |
| 자동 태그 부여 실패 | 답변은 정상 저장, 사용자가 수동으로 태그 추가 가능 | Requirement 5.3 |
| 브라우저 로컬 저장소 사용 불가 | 일기 기능 비활성화 + 사유 안내 | Requirement 11.4 |
| 유효하지 않은 초대 코드 | 진입 거부 + 안내 메시지 | Requirement 1.2 |
| 다른 초대 코드 기록 접근 시도 | 소유권 검증 실패로 요청 거부 | Requirement 14.2 |
| 기록이 없을 때 내보내기 | 내려받기 버튼 미표시 | Requirement 6.3, 7.4 |
| 소재 추천 결과 없음 | 안내 메시지 표시 | Requirement 8.3 |

모든 오류 상황에서 AI 결과는 검증을 통과하기 전까지 DB에 저장하지 않으며, 실패가 서비스 전체 중단으로 이어지지 않도록 각 모듈은 독립적으로 실패를 격리한다.
